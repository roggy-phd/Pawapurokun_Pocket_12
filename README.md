## 注意

- **このリポジトリにはゲームのROM、セーブデータ、エミュレータのステートセーブは含まれていません。** 各自が所有するゲームカードから吸い出したROMに対して使うことを前提としています。
- ROMパッチ作成ツールは、改造していない初版ROM（`PAWAPOKE12_VPTJA4_00.nds`、SHA1 `4327f56f23729a59d44bd170e0ed53a2bb4667dd`）にだけ対応しています。
- 改造は自己責任でお願いします。セーブデータは必ずバックアップを取ってください。

## ROMパッチ作成ツール（v31）

```bash
python rom_patcher/PowerPoke12_ThirdPitch_v31.py
python rom_patcher/PowerPoke12_ThirdPitch_v31max.py
python rom_patcher/PowerPoke12_ThirdPitch_v31.py 元.nds 出力.nds
```

引数なしで起動すると編集ウィンドウが開きます。コマンドラインでは `--config sets.json` で設定ファイルを指定できます。設定ファイルを指定しない場合は、`--edition normal|max` で初期セットを選べます。

通常版とmax版は追加球種の仕組みと上限が同じで、初期セットが違います。今回の配布コードでは、「同じ球種でもLvが違えば別の球として読む」は通常版・max版・unlimited版とも初期値ONです。

### 2026-10-16更新：ジャイロボールの発動判定を球種そのものに

ジャイロボールは特殊能力で、**全力で直球を投げたときに球種IDだけが専用の値（`0x18`）へ書き換わり、
表示名・見かけ球速・スタミナ消費がジャイロのものに変わります**。球種枠も変化量も触らないので、
軌道はストレートのまま。「名前が変わって速く見えて、その分疲れる」という挙動です。
アクション野球ではB連打、オーペナでは力の入れ具合（`PSel+4`）が4以上のときに発動します。

この判定が**球種コード5（ストレート系の第1枠）限定**になっていました。同じストレートでも、
第2球種枠に置いた場合やv31の追加球種として持たせた場合は発動しません。球種としては同じものなので、
**球種ID（ストレート＝5）で判定する**ように変更しました。`--no-gyro-by-id` で従来の挙動に戻せます。
**初期値ON**。

- 対象になるもの：ストレート第1枠、**ストレート第2枠**、**追加球種のストレート（Lv1〜7のいずれも）**
- 対象外のまま：ムービングファスト、ツーシーム、超スローボール、オリジナル変化球

追加球種は投球時に実際の球種IDが書かれるため、Lvを問わず拾えます。

変更は ov10 の2か所、`0x021695A4`（球速側）と `0x021698B0`（スタミナ側）の `LDRB` の
オフセットを1から0に変えるだけです。追加コードはありません。

### 2026-10-15更新：第2球種枠の取りこぼし3件を修正

`HenkaV` の件を調べる過程で、**同じ型の取りこぼしが投球処理にあと5か所**見つかりました。いずれも
「球種コードを第1枠の値とだけ比べている」「球種IDで引くべき表を球種コードで引いている」という、
第2球種枠の追加に周辺処理が追いついていない形です。3つのオプションにまとめ、**初期値ON**で入れています。

| オプション | 対象 | 内容 |
|---|---|---|
| `--no-control-slot2` | ov10 `0x0216934C` | 制球計算で、フォーク系・シンカー系に −20 のペナルティが入るのはコード2・3（第1枠）だけ。コード9・10（第2枠）は免れていた |
| `--no-batjudge-slot2` | ov15 `0x021A7898` / `0x021A7904` / `0x021A7AE8` | 打撃判定で、見かけ球速が速いストレートの +1 補正（2か所）はコード5のみ、フォーク系の落差補正（変化量Lv×3）はコード2のみ。コード12・9は対象外だった |
| `--no-stamina-orig` | ov10 `0x0216986C` | スタミナ消費の球種別テーブル（球種IDで引く表）を、オリジナル変化球のときだけ球種コードで引いていた |

実装はどれも「第2枠のコードを系統に畳んでから元の比較に渡す」形で、**修正後の挙動は第1枠とまったく同じ**です。
スタブは ov10 のデッドエリア `0x0219211C`〜`0x02192198`（制球16B、打撃判定16B×3、スタミナ60B）に置き、
ov15からは長距離分岐で到達します（既存の読み修正と同じ方式）。ARM9・他のオーバーレイは変更しません。

**比較の手順**：3件とも既定で有効です。修正前の挙動と比べたいときは `--no-control-slot2` /
`--no-batjudge-slot2` / `--no-stamina-orig` を個別に付けてROMを作り、同じステート・同じチーム割り当てで
回してください。3つすべてを外した出力は2026-10-14版の出力と完全一致します。

なお制球の件については「特定球種はID、系統はコード」という分担が意図的だった可能性も残ります。
修正内容は第2枠を第1枠と同じ扱いにするだけで、新しいバランスを作ってはいません。

`--stamina-orig` は、オリジナル変化球を第2球種枠に持つ選手にしか影響しません。通常の選手ではオリ変は
第1枠に入るため、既定構成では出力に差が出ません。

**スタミナの件について**：同じ関数の球速側（`0x02169650`）は、オリジナル変化球に対して
`0x020C0C06` の選手別レコード（1サイド528バイト、1選手44バイト）から**ベース球種の番号**（1始まり）を
読み、`(番号−1)` で表を引いています。スタミナ側だけが球種コードで引いていました。コード0〜5は偶然
各系統の基本球種に当たるため第1枠では妥当な値になりますが、第2枠（コード7〜12）ではパーム・ナックル・
Vスライダー・SFF・チェンジアップ・スローカーブという無関係な球種の値が使われます。
`--stamina-orig` は球速側とまったく同じ参照を再現します。この分岐は**実際に投げる球がオリジナル変化球の
ときにしか入らない**ため、ベース球種番号が0（オリ変なし）になることはなく、`−1` のアンダーフローは
起きません。スタブ内の命令はどれもフラグを変えないので、後続の条件実行チェーンも保たれます。

### 2026-10-14更新：第2球種の変化量が0として扱われるバグの修正

オーペナで、**各系統の第2球種の変化量が常に0として扱われていました**。4版すべてに修正を入れています。
GUI表記は「オーペナ: 第2球種の変化量が0として扱われるバグを修正（CPUの球種選択と打者の読みに影響）」、
CLIは `--no-second-strength`。**初期値ON**です。

**仕組み**

パワポケ12には、球種コード（何系統の何番目の枠から投げたか）を渡すと変化量Lvを返す関数が2つあります。

| 関数 | 入力 | 返す値 |
|---|---|---|
| `0x0216D494` | 球種コード | コードを7で割って系統と枠に分解し、**第1枠・第2枠どちらのLvも正しく返す** |
| `0x02170580` | 球種コード | `0x0216D494` の薄いラッパー。**コード7〜12で問答無用に0を返す** |

```
0x02170580:
    コード6（スローボール）  → 0
    コード7〜12（第2球種枠） → 0      ← ここ
    コード0〜4             → 0x0216D494 を呼ぶ（Lv、6で頭打ち）
    コード5（ストレート）    → 球速から算出（0〜6）
```

中で呼んでいる `0x0216D494` は第2枠を正しく扱えるのに、ラッパー側が手前で弾いています。

**何が起きていたか**

`0x02170580` を呼んでいるのは、オーペナの球種選択と読みに関わる関数です。

- `UcdMin`（打者の「状況に応じた球」）×3 — しきい値が1以上なので、**第2球種は予想候補に上がらない**
- `UcdMax`（持ち球で一番強い球を選ぶ）×3 — 最大値比較で**第2球種が必ず負ける**
- `UcdRnd`
- ov15の打球判定1か所 — **実際に投げた第2球種の強さも0になる**

**【2026-10-16 訂正】** この節には当初「CPUが第2球種を投げる唯一の経路は、ストレート系のコード5→12の
30%振替だけ」「`UcdSel` も影響を受ける」と書いていましたが、**どちらも誤りでした**。

`UcdSel`（`0x02170664`）は `HenkaV` を経由せず、変化量取得関数 `0x0216D494` を第1枠と第2枠に対して
直接2回呼び、`L2 / (L1 + L2 + 1)` の確率で第2枠を選びます。Lv7同士なら約47%。この経路は
`UcPitSub4` / `UcPitSub6` → `Ucd244f` → `UcdSel` として原作から正常に機能しており、
**第2球種はもともと普通に投げられています**。

したがって `HenkaV` が0を返すことの実害は、(1) `UcdMax` / `UcdMin` を使う別経路での候補評価、
(2) 実際に投げた第2球種の打撃判定用の強さ、の2点に限られます。

なおアクション野球側（ov3）は `0x0216D494` を17か所で直接呼んでいるため、**影響を受けていません**。
この問題はオーペナ専用です。

**修正内容**

`0x02170594` をフックし、コードごとに次のように振り分けます。

| 球種コード | 修正後の扱い |
|---|---|
| 0〜6 | 変更なし（元の処理へ戻す） |
| 7〜11（スライダー系〜シュート系の第2枠） | `0x0216D494` で実際のLvを取得、6で頭打ち |
| 12（ストレート系第2枠） | コード5と同じく球速から算出 |
| 13以上 | 変更なし（0を返す） |

コード12だけ扱いが違うのは、ストレート系第2枠に入るのがムービングファストやツーシームといった
速球系で、変化量より球速が投球の質を決めると判断したためです。ただしこれは設計判断であり、
`0x0216D494` で実Lvを返す実装も成り立ちます。球速165km/hの投手ではコード12が常に上限の6になり、
コード5と同点になる点に注意してください。

- 追加領域：ov10 `0x021920E0` に60バイト（profiler文字列領域。元バイトを照合してから書き換え）
- 既存命令の置換：1か所×4バイト
- ARM9・他のオーバーレイは変更しません

**既知の未修正点**：全力投球（力の入れ具合4以上）でストレート第1枠を投げたとき、特殊能力によっては
球種別スタミナ消費を強制的にフォッシュ（最大値+2）として計算する処理があります（ov10 `0x021698B4`）。
これもコード5限定で、第2枠のツーシームやムービングファストには掛かりません。ただし他の5件と違い、
修正すると第2枠が**不利になる**方向のため、入れていません。

**検証**

4版とも元ROMから生成して展開し、フック・スタブ・4つの追加領域（`0x021920E0` 第2球種／`0x021921C4`
走者NULL／`0x021925C8` 責任投手／`0x02192600` 追加球種表）が重複しないことを確認しました。
**OFFにした出力は2026-10-13版の出力と完全一致**します。

**成績への影響に注意してください。** この修正はオーペナの球種選択と読みの両方を変えるため、
これまでの検証で出した被読率や投手成績は、すべて修正前の数値です。修正前後の比較を行う場合は
`--no-second-strength` で従来の挙動のROMを作り、同じ条件で回してください。

### 2026-10-13更新：走者の責任投手が失われるバグの修正

DSi実機のクラッシュ（外野への打球で赤画面）をRAMダンプから追跡し、原因を特定しました。名前は **v31 / v31max / v31unlimited / v31unlimited_original_plus のまま**、4版すべてに同じ修正を入れています。GUIの表記は **「オーペナ/試合: 走者の責任投手が失われるバグを修正（状態復元時に現在の投手を設定）」**、CLIは `--no-runner-owner-fix` です。**初期値ON**。

**何が起きていたか**

走者の管理レコードには、その走者の失点を誰の責任にするかを指す欄（`+4`）があります。走者が進塁・生還するたび、ゲームはこの欄をたどって投手の記録を更新します。

四球 `FourBallCom`（`0x0217C42C`）、死球 `DeadBallCom`（`0x0217C4F8`）、走塁判定 `UpDsenChk`（`0x02179DE8`）、および `0x021644EC` と、走者が塁に出る経路はすべてこの欄を設定し、塁を移るときはスロット移動処理 `0x0216CF54` が `0x0216D01C` で引き継ぎます。**例外は試合状態の復元処理 `0x0215AB88` だけで、最後のループ `0x0215AC44` が4つの塁の在塁状態を保存データから復元する一方、`+4` には触れません**（保存データ側にその欄がないため）。塁を空にする処理 `0x0216CEFC` も `+4` を消さない作りなので、一度も使われていない塁が「走者あり・責任投手なし」で復元されると、誰も直せないまま残ります。

その状態で走者が動くと、`0x0216D364` がアドレス `0x00000004` を読みに行って停止します。DSi実機では赤画面になります。**元ROMから存在する不具合**で、投手交代が多いほど踏みやすくなります。

**修正内容**

復元ループで各塁の在塁を書き戻した直後に、責任投手の欄へ現在の投手（`[0x020D0F0C]+0x0C`）を設定します。復元時点でもっとも妥当な帰属であり、**自責点・得点の計上も通常どおり行われます**。走者の更新そのものを飛ばす方式と違い、記録が欠けません。

- ov10 `0x0215AC44` の1命令をフックし、未使用領域 `0x021925C8`（`HS_STATE+8` と `OV10X` の間の56バイト）に48バイトのコードを追加
- 2026-10-12のNULL参照対策（`0x0216D318` 入口、`0x021921C4` に44バイト）も保険として残しています。通常は発動しません
- ARM9・他のオーバーレイは変更しません
- `--no-runner-owner-fix` / `--no-runner-null-guard` で個別に外せます

**あわせて修正：NULL参照対策スタブの配置**

## ROMパッチ作成ツール（v31unlimited）

v31をベースに、**セットF（15）だけ追加球種の上限を50枠から189枠に拡張**した版です。セット1〜14は従来どおり50枠まで使えます。

```bash
python rom_patcher/v31unlimited/PowerPoke12_ThirdPitch_v31unlimited.py
python rom_patcher/v31unlimited/PowerPoke12_ThirdPitch_v31unlimited.py 元.nds 出力.nds
python rom_patcher/v31unlimited/PowerPoke12_ThirdPitch_v31unlimited.py 元.nds 出力.nds --config rom_patcher/v31unlimited/v31unlimited_default.json
```

- 初期設定のセットFには、追加可能な通常27球種のLv1〜7をすべて登録しています（27×7＝189枠）。超スローボール、通常ストレートのLv違いも含みます。オリジナル変化球は追加候補に含めません。
- 球種・Lvはウィンドウで編集・削除でき、設定はJSONで保存・読込できます。
- 189枠は追加設定表の枠数です。基礎12枠と重複する組み合わせも含むため、単純に「12＋189＝201種類の独立した球種」になるわけではありません。
- 各系統の先頭追加球は基礎との重複でも使い、2個目以降は基礎と同じ球種・Lvなら使わない、というv31の仕様を維持しています。
- 各系統の基礎2枠が埋まっていること、選手のbyte92上位4bitでセットを選ぶことも従来どおりです。選手にセットFを指定すると、そのROMの拡張セットを使います。
- 既存のセット配置を維持してFの末尾だけを拡張しています。設定表は840→979バイト（1か所あたり139バイト増）で、既存の確保領域内に収まります。
- 従来版と同じく、**改造していない元ROMから作成**します。適用済みv31への重ね掛けはしません。

「unlimited」は従来の50枠制限を解除した名称で、無限に追加できる意味ではありません。また、全Lvを登録すると低Lvの球もCPUの投球候補に入るため、球種数が最大でも、従来の62球種の最強Fより強いとは限りません。

元ROMからの生成・再展開一致検査と、ARM命令を実行した追加球種参照・境界の591件の検査は通過しています。試合動作・DSi実機・オーペナ成績は別途検証が必要です。

検証コードを実行する場合のみ `unicorn` が必要で、パッチ作成ツール自体は標準ライブラリのみで動作します。

## ROMパッチ作成ツール（v31unlimited_original_plus）

v31unlimitedをベースに、**セットFにオリジナル変化球を6枠まで追加できる**ようにした版です。上限は189枠から195枠になります。

- オリジナル変化球はセットFでのみ、各系統の2行目以降にだけ置けます。1行目は選手が同じ球を持っていても必ず使われる枠なので、方向の合わない選手で事故を起こすため禁止しています。
- オリジナル変化球には系統（方向）の情報が選手側に入っています。**ROM側に方向判定を追加**してあり、その系統の第1枠か第2枠にオリジナル変化球を持つ選手のときだけ使われ、持たない選手では自動的に飛ばされます。そのため、同じセットFを別の選手に付けても壊れません。
- 画面下の「セットF: オリジナル変化球の追加球種も使う」にチェックを入れ、系統を選ぶと、オリジナルLv1〜6の6行が追加されます。個別に編集・削除もできます。
- 既定をLv1〜6にしているのは、Lv7が多くの選手の持つオリジナル変化球と完全一致して自動で飛ばされるためです。
- 理論上の最大は **27球種×Lv1〜7＝189 ＋ オリジナル変化球1＝190球種**です。基礎12枠の中身は189の側にすべて含まれるので、重複して数えません。
- **オリジナル変化球のLv違いが、アクション野球で正しい軌道で描画されるかは未検証です。** オーペナは描画を伴わないため影響しません。
- 追加球種を増やしても強さが上がるとは限りません。オーペナ検証では62球種と190球種で有意差が出ていません。

## カード野球について

今回の追加球種拡張はアクション野球・オーペナ向けで、カード野球の投球カード生成や読み判定を追加球種対応にする改造は入れていません。

カード野球にも「読み」はありますが、確認した対決計算では球種名・Lvを個別に照合せず、方向グループと第1／第2枠の一致によって0・4・9の加点を行います。投球カード生成も既存の14枠を参照する構造で、追加球種表を列挙しません。この14枠は内部の参照枠数であり、手札の枚数ではありません。

同じグループ・枠にまとめる限り、球種数を増やすだけではオーペナのように「候補が増えて読まれにくくなる」効果を作れません。対応するにはカード生成・分類・読み判定を別途設計する必要があるため、今回の改造範囲には含めていません。

## オーペナでの検証結果（ざっくり）

- **v28（原作の読みのバグそのまま）**：最強選手6人×16シーズンで、第三球種を足しても防御率の差は検出されませんでした（どの投手も平均0.7〜0.9）。
- **v31（読みのバグ修正＋追加球種を別の球）**：5シーズン。基本12球種＋セットF 50球の「62球種の最強F」が、防御率0.58・奪三振12.5/9で、5シーズンすべて防御率1位。他の最強5人は防御率0.95〜1.20でした。最強Fとの差は、最強Eを除く4人では有意、最強Eとの比較はp=0.055でした。
- 打者の読みのバグ（番号の取り違え・サインバレ）は、DS甲子園（初期版・ベスト版とも）の自動試合から同じ処理が引き継がれていたものです。

v28の詳細は `docs/openpenna_verification.md`、v31の詳細はnote記事③を参照してください。ここに掲載した成績は守備対策統合前のROMでの結果です。v31unlimitedを含む検証の詳細はnote記事③を参照してください。同名でも、守備対策の追加でROMのSHA1は変わります。過去の成績と対応するROMのハッシュは、記事に記載したものを参照してください。
