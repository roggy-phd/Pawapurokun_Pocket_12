## A. 確定した事項

### A-1. ストレートのLvは、オーペナの1球ごとの処理では一度も読まれない — CONFIRMED

**根拠1（静的）**：ROM全体（ARM9・全オーバーレイ）で、投球の枠のLvを取り出す処理は次の2系統だけ。
- 汎用のLv取得関数 `ov10 0x0216D494`（コード→枠→Lv＋能力補正）
- 変化量の計算 `ov10 0x02169C54` / `0x02169D8C`（球種ごとの係数表 ×（Lv＋2）。内部で`0x0216D494`を呼ぶ）

それ以外で枠のLvを読むのは、画面表示（カード、個人データ）、実況の台詞選び（`0x02167C54`）、
サクセス（ov5）だけ（`lsr #5` / `lsl #0x18; lsr #0x1D` / `and #0xE0`の全件走査による）。

`0x0216D494`をコード5（ストレート）で呼ぶ経路は、
- `0x02170590`：コード5のときは**球速から計算する分岐**に入り、`0x0216D494`は呼ばない（`0x021705AC bne` の先）
- `0x02170674`：系統5のときは コード5 をそのまま書くだけ（Lvを使わない）
- `0x02169C54/0x02169D8C`：呼び出し元は ov10 `0x02172C58`、`0x02173FAC`、`0x021747D0`、`0x02174C00`、`0x021752F0`、ov3（アクション野球）

**根拠2（実行）**：オーペナ中のステート（v23 ml3）で、両チームの投手12人全員の枠をストレートLv7／Lv1に書き換え、
自動試合の1球分の処理（ov15 `0x021A6A88`、戦術→球種選択→投手補正→振る/見送る→判定→打球処理の入口まで）を
1500〜4000回実行。
- 実行された基本ブロックの回数：Lv7とLv1で**完全一致**（全ブロック）
- 打撃結果番号の分布：**完全一致**
- `0x0216D494`がコード5で呼ばれた回数：**0回**
- `0x02169C54`・`0x02169D8C`・`0x02172C58`・`0x021747D0`など、変化量・狙い球系の関数：**1回も実行されない**

**結論**：オーペナの自動試合で、ストレートの枠のLvが打撃結果に影響する経路は、1球ごとの処理の中にはない。
ストレートLvが効くのは、アクション野球（ov3・ov10の変化量計算と、CPU打者の狙い球の処理）だけ。

**残る可能性**（UNKNOWN、最小の未確認範囲）：1球分の処理の外側、すなわち打球が前に飛んだ後の処理、
投手交代・疲労、試合単位の集計。ただしこれらでストレートの枠を読むには、上の2系統の関数を通るか、
枠を直接読む必要がある。直接読むコードは走査で見つかっていないため、**ストレートLvはオーペナの結果に影響しない**
可能性が高い。過去のシーズン比較で見えた差は、偶然の揺れの範囲だった可能性を否定できない。
**同じ乱数状態からの比較**（後述 §17の方法）で確定させることを推奨する。

### A-2. 6球種と12球種：1球ごとの処理では12球種の方がわずかに不利 — CONFIRMED（1球ごとの範囲）

同じエミュレーションで、各系統の2枠目を空にした6球種版と12球種版を比較。
- 結果番号の平均：6球種 4.89、12球種 5.07（大きいほど打者有利）
- 12球種版は2枠目（コード7〜12）を投げるが、投手補正の基本値（`0x02170590`）は2枠目のコードで**0**になる（`0x0217059C cmp r0,#5; bls` → 5超は`mov r0,#0`）

**「球種の数が多いと打者が迷う」という式は、1球ごとの処理には存在しない**（CONFIRMED）。
- 配球履歴の参照（`0x02173160`）は、1/N のような分母を持たない（下のA-4）
- CPUの球種選択（`0x02170674`）は、系統を戦術が先に決め、その中でL1:L2の比で選ぶだけ

したがって、記事の「12球種の方が圧倒的に良い」という観測を説明する処理は、1球ごとの処理の**外**にある
（UNKNOWN、A-1と同じ未確認範囲）か、比較した2人の投手が球種数以外でも違っていた可能性がある。

### A-3. 投手補正の基本値 `0x02170590` — CONFIRMED

```
def base_correction(code):               # ov10 0x02170590（0x02170580はプロファイラ用の入口）
    if code == 6: return 0               # スローボール
    if code > 5:  return 0               # 2枠目のコード（7〜12）はすべて0
    if code < 5:
        v = level_getter(code)           # 0x0216D494（能力補正込み）
        return min(v, 6)                 # 0x0217064C: cmp r0,#6; movhi r0,#6
    # code == 5（ストレート）: 球速から計算
    s = speed_value()                    # 0x0216D6E8
    v = 0 if s < 0x88 else (s - 0x88) // 4 相当   # 正確な式は 0x021705B0〜0x02170640
    if 鉄腕: v += 1                       # +0x18 bit27 → byte93 bit3（名前の対応は要確認）
    if (ノビ○ or ノビ◎) and 条件: v += 1   # 両方あっても+1のみ
    if 速球中心: v += 1
    elif 変化球中心: v -= 1
    return min(v, 6)
```

### A-4. 配球履歴の参照と一致判定 — CONFIRMED（処理）／TENTATIVE（意味付け）

**履歴の書き込み**（`ov10 0x021684E0`〜`0x0216852C`）：`+0x2F9→+0x2FA … +0x2F6→+0x2F7`とずらし、
**選択構造体の+0（表示用コード）**を`+0x2F6`に入れる。

**参照コードの生成**（`ov10 0x02173160`→`0x02173170`）：
```
r = rand(18)                  # 0..18（0x020591B8 は rand(n) = x % (n+1)）
if   r <= 1:  ref = 5
elif r <= 5:  ref = hist[0x2F6]
elif r <= 8:  ref = hist[0x2F7]
elif r <= 10: ref = hist[0x2F8]
elif r == 11: ref = hist[0x2F9]
elif r == 12: ref = hist[0x2FA]
else:         打者の性質バイト（+6）による条件分岐で、確率的に 0x021707D0（持ち球からLv比で抽選）か 5
if 投手がストレート2枠目を持ち ref == 5: 50%で ref = 12
```

**一致判定**（`ov15 0x021A7758` / `0x021A7784`）：`ref == 選択構造体+1（球種コード）`

**重要な発見：履歴は表示用コード、比較は球種コード**。基本球種（普通のスライダー、カーブ、フォーク、シンカー、シュート、ストレート）は
表示用コード＝球種コードなので一致しうるが、特殊変化球（SFF=0x0A、チェンジアップ=0x0E、ナックル=0x08など）は数字が違い、
**履歴からはほぼ一致しない**。数字が偶然一致する組み合わせもある（例：SFFの表示0x0A＝シンカー系2枠目のコード10）。
元のゲームの書き間違いの可能性が高い（TENTATIVE）。

**一致の効果**（`ov15 0x021A7954`、再確認済み）：一致して、かつ振る判定のとき
```
if 状態+0x13 & 0x30:              # 毎球作られるコース属性（際どいコース／ボール球の可能性）
    if rand(99) < 50: 0x021A79D4    # ボールとして見送る（打者有利）
    else:             +0x16 += 2    # 振りにいく。投手補正+2（投手有利）→ 打撃結果へ
else:
    打撃結果へ（補正の追加なし）
```
一致しない場合（`0x021A78E8`/`0x021A787C`）は、見送りの分岐がなく、そのまま振る（球速150/147超のストレートなら+1）。
→ **一致の効果は一方向ではない**。際どい球でだけ効き、「半分は見送ってボール（打者有利）、半分は手を出して打ち取られやすい（投手有利）」。
四球と三振のどちらが増えるかは、ボール1つの価値と補正+2の価値の比較になるため、正味の有利不利は UNKNOWN。
（以前の版の「一致は投手有利」という記述は単純化しすぎていたので訂正する）

### A-5. 打撃結果の式 — CONFIRMED

```
# ov15 0x021A77F8
b = min(batter_value(打者) // 2, 7)     # 0x0216DC64: 打者の能力フラグ(+0x28/2C/30)と状態から1〜15
idx = b - corr16                        # corr16 = 状態の+0x16（符号付き）
if idx < 0: idx = 0
idx += rand(8)                          # 0..8
idx = min(idx, 15)
dispatch(TABLE_021B51B4[idx])           # 0〜2 → 0x021A7BF4（ストライク。3つで三振）
```

`+0x16`の初期値は`base_correction(実際の球種コード)`（`ov15 0x021A706C`）で、その後に状況による加算、
能力による加算、一致判定の+2などが足される（内訳は §5、一部 UNKNOWN）。

### A-6. 保存能力ビットと実行時フラグ — CONFIRMED

変換はなく、そのままの配置：
- 選手データ `+0x28/+0x2C/+0x30` ＝ パスワード byte70–81（野手能力）
- 投手データ `+0x14/+0x18` ＝ byte86–93（投手能力）
- ワードのビットb → byte(基準＋b/8) の bit(b%8)

根拠：ノビ○（+0x14 0x08000000）とノビ◎（+0x18 0x8000）が同じ関数で○◎の関係として使われ、
速球中心（+0x18 0x80）→+1、変化球中心（0x100）→−1、闘気（打者+0x30 0x100000）と気迫（投手+0x18 0x80000000）が組で判定される。
334か所の判定一覧：`pp12_ability_flag_xrefs.csv`

### A-9. パスワード登録時の統合処理 — CONFIRMED

### A-10. サブポジ○バグ — CONFIRMED（原因）／UNKNOWN（影響の大きさ）

ov3 `0x021155AC`の末尾（`0x02115764`〜）で、サブポジ○なら不適合度−1（`& 0xFF`）。
メインポジション（0）では 0−1＝255 → 上限6に丸め → **最悪の不適合度**になる。

不適合度0〜6の意味、位置ごとの表、エラー率への効き方、「エラー」能力との関係は**未解析**。

## B. 訂正した過去の仮説

1. 「`0x02173160`＝CPU打者の読み」→ 履歴から参照コードを作る処理。一致の効果は、際どい球で「50%見送りボール／50%投手補正+2」で、一方向ではない（A-4）。

3. 「打撃結果の式に球のLvは入っていない」→ **誤り**。`+0x16`の初期値として入る（1枠目のみ、上限6）。
4. 「2枠目は役に立たない」→ **不正確**。CPUの選択（L1:L2）と参照コードの抽選では使われる。
   補正の基本値`0x02170590`でだけ0になる。
5. 「ov17がオーペナの本体」→ **誤り**。ov17はパスワード登録の処理。オーペナはov15＋ov10。

## C. 第三球種（オーペナ）— CONFIRMED（仕組み）

**割り込みの位置**：CPUの戦術による球種選択`0x02172308`の最後（`0x021723F4`）と、通常試合の`0x02172B64`。
オーペナは`0x021722F8`を直接呼ぶので、前者で捕捉できる。

**各処理から見えるもの**

| 処理 | 実行のタイミング | 第三球種は見えるか |
|---|---|---|
| CPUの戦術・系統の決定（`0x0217222C`、`0x021722F8`の前半） | 差し替え前 | **見えない**（2枠のみ） |
| 1枠目か2枠目かの選択（`0x02170674`） | 差し替え前 | 見えない（L1:L2） |
| パッチの差し替え（L1:L2:L3で抽選） | 選択の直後 | ― |
| 補正の基本値`0x02170590` | 差し替え後 | **見える**（1枠目のコードとして。Lvは上限6） |
| フォーク系の特別処理（`0x021A7AD4`、コード2） | 差し替え後 | フォーク系の第三球種は**コード2の処理に入る** |
| 履歴への書き込み（表示用コード） | 差し替え後 | **見える**（第三球種の表示用コードが記録される） |
| 参照コードの抽選`0x021707D0` | 差し替え中 | 1枠目の代わりに第三球種を見る |
| 一致判定 | 差し替え中 | 球種コードは1枠目と同じ |

**効果の実測**（1球ごと、同じステート）：
- 最強（全枠Lv7）：結果番号平均 5.03 → 4.93（ほぼ変化なし）
- 弱い投手（全系統2枠ともLv2）＋Lv7の第三球種：平均 5.13 → 4.87、ストライク22.1%→25.0%、打者有利の結果24.5%→20.8%

**結論**：第三球種は「2枠目（基本値0）を投げる機会の一部を、Lvのある1枠目扱いの球に置き換える」効果が中心。
元の持ち球が弱いほど効き、Lv7で揃った投手では見えない。
本来の「3つ目の枠」と同じ扱いにしたいなら、2枠目のコード（c+7）として投げさせる方式にする必要がある（基本値0になる）。
どちらを「正しい」とするかは設計判断。

## R. v26d ペナント入れ替わり修正の監査

**コードの意味**（CONFIRMED、ステート①〜⑦とov5 `0x020EDAA0`・ov15 `0x0219F9EC`から）

| 値 | 上位4ビット | 下位4ビット |
|---|---|---|
| 変換前（ペナント開始〜初回セーブ前） | `F`＝アレンジチーム | アレンジファイル番号−1（0〜11） |
| 変換後（初回セーブ以降） | `F` | ペナント内の枠番号（0〜5） |
| 通常の球団 | `0` | 球団番号（0〜11） |

実例：開始時 `F1 F6 F7 F2 FA F5` → 初回セーブ後 `F0 F1 F2 F3 F4 F5`

**「枠0＝アレンジ1」になる理由**：2回目以降のセーブで、変換後のコード`F0`をファイル番号として読み直すため、
枠0にアレンジファイル1が読み込まれる。

**修正の安全性**
- アレンジチームを使わないペナント：`tst #0xF0`で今までどおり飛ばす → **影響なし**
- アレンジチーム1つ／複数：初回セーブで正しく変換、2回目以降はすべて読み込みを飛ばす → **保持**（エミュレーションで確認）
- 初回セーブ時に「ファイル番号＝枠番号」のチーム：読み込みを飛ばすが、開始時の領域はアレンジファイル順なので**同じ選手が既に入っている**（ステート①で確認）
- CPUチーム・自分のチーム：コードの扱いは同じなので区別なく動作
- 旗、成績、リーグの並び：コード以外に触らないので影響なし（旗はそもそも入れ替わっていなかった）

**弱点**（TENTATIVE）
- 初回セーブの前に、選手データの領域がアレンジファイル順以外に並び替えられる操作があると、「ファイル番号＝枠番号」のチームで誤りうる（ステートでは確認できていない）
- 初回セーブ以降、アレンジチームを編集してもペナントに反映されない（元のゲームで反映されているように見えたのはバグによるもの）
- すでに入れ替わったセーブは直らない

**よりきれいな修正**（参考）：変換で元のファイル番号を失わないように、別の場所に保存する方法。
ただし、コードの下位4ビットを枠番号として読む処理（ov15 `0x021987B0`など）が複数あり、変更範囲が大きい。
**v26dの方式で実用上は十分**と判断する。

## §17 推奨する検証方法

**同じ乱数状態からの比較**：オーペナで試合開始直前のステートを1つ取り、
その投手データだけを書き換えたセーブ（例：ストレートLv1とLv7）で**同じステートから**「試合進める」を実行して、
結果（スコア、投球数）が1球目から変わるかを見る。
乱数の状態はステートに含まれるので、処理に違いがなければ**試合結果が完全に一致**するはず。
一致すれば「影響なし」が確定し、違えば最初に食い違った場面を調べれば、影響する処理を特定できる。
（melonDSのRAM書き換え機能、またはチートコードで投手データのバイトだけを変えるのが簡単）
